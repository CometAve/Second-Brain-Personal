# 웹 UI/UX 개선 기록

이 문서는 2026-09-26까지의 로컬 구현과 검증을 요약한다. 상세한 선행 결함과 저장·세션 경계는 [기반 안정화 기록](foundation-review.md)에 있다. 아래의 검사는 당시의 코드와 QA 데이터에서 실행한 결과이며, 현재 작업 트리의 모든 UI 경로가 완료됐다는 뜻은 아니다. 이 문서와 화면 자료는 커밋·푸시·PR·병합의 증거가 아니다.

[화면 자료 갤러리](ui-ux-evidence/index.html)는 로그인·메인·타이포그래피 전후, 현재 로고의 각도와 연속 회전, 대표 로딩 전환을 모았다. [로고 형상 근거](ui-ux-evidence/loading-logo-geometry.md)는 원본 좌표와 추정 깊이를 구분한다. 원본 한 장으로 뒷면의 정확한 3D 형상을 증명할 수 없다. [렌더러 비교 페이지](ui-ux-evidence/loading-live.html)는 실제 `drawLogoFrame`을 쓰지만 앱 라우트가 아니며 검수용 시계를 사용한다.

간결한 검사 결과 원문은 [렌더러 9항목](ui-ux-evidence/loading-logo-motion-result.json), [앱 로딩 19항목](ui-ux-evidence/motion-result.json), [그래프 카메라 7개 fixture](ui-ux-evidence/graph-camera-result.json), [목록 포인터 8항목](ui-ux-evidence/list-pointer-result.json)으로 남겼다. 결과 파일의 합성 조건과 QA 경로를 실제 사용자 데이터의 검증으로 확대하지 않는다.

이 자료는 확인 후 수동으로 선별해 문서에 넣은 스냅샷이다. 재실행 때 자동 생성되는 화면·영상은 무시되는 `.playwright-cli/` 작업 영역에 두고, 검토할 자료만 갤러리로 옮긴다. 기존 로딩 전환 검사 재현에는 production preview `http://localhost:4173`와 별도 QA fixture 노트 95·90이 필요했다. 별도의 목록 포인터 8항목 기록은 QA 노트 104를 사용했다. 이 fixture의 존재나 서버 실행 상태는 문서만으로 보장되지 않는다.

## 확인된 결함과 수정 범위

- 이미지가 서버 GET에는 남아 있는데 새로고침 뒤 편집기에 보이지 않던 문제는 Milkdown 이미지 블록의 `title: null` 처리에서 재현했다. 빈 제목만 정규화한 뒤 실제 POST/PUT/GET과 새로고침에서 픽셀 표시를 확인했다.
- Crepe 목록의 `UL > DIV > LI` 구조가 의미 검사에 실패했다. 공개 노드 뷰로 `LI`를 직접 렌더링하고 중첩·할 일·키보드·저장·재조회 24항목을 확인했다. 포인터로 항목을 다른 목록에 옮긴 직후의 번호 표식과 저장 후 순서·텍스트·체크 상태도 확인했다.
- 사용자가 본 회전 로고의 옆면이 부자연스러웠다. 35점 형상의 큰 평면과 긴 관통선을 줄인 현재 고정 구조로 교체하고 여러 각도와 실제 회전을 보았다. 깊이와 뒷면은 추정이다.

## 성능 측정과 한계

2026-09-26 마지막 변경 뒤의 Lighthouse 13.4.1 cold 측정은 로그인 후 메인 **74/100/100/100**(성능/접근성/권장사항/SEO), FCP 622ms, LCP 2,447ms, TBT 285ms, CLS 0이었다. 인증된 노트는 **87/100/100/100**, FCP 483ms, LCP 2,454ms, TBT 10ms, CLS 0이었다. 둘 다 별도 QA 데이터와 로컬 production preview에서 한 번씩 측정했다. 메인 측정에는 저장 노트 2개, desktop simulated 40ms/10Mbps/CPU 1 조건이 쓰였다. 노트는 QA 쿠키를 사용한 별도 Chrome의 desktop preset·빈 브라우저 캐시 조건이며 최종 URL이 노트 화면임을 확인했다.

이전에 관찰한 메인 **100/100/100/100**은 warm 조건이다. cold 74점과 같은 조건의 전후 비교가 아니며, 100→74를 코드 변경의 성능 악화량으로 해석하지 않는다. 이전 노트 측정 83/93/100/100과 88/100/100/100도 마지막 변경 전 각 한 번의 기록이어서 작은 차이의 원인을 특정할 수 없다. 같은 QA 노트에서 캐시를 끈 로컬 자산 전송 합계는 3,487,622→2,319,451바이트였다. 해당 화면의 전송량이며 실행 속도 개선률은 아니다.

cold 메인의 초기 script evaluation 약 1,067ms와 긴 작업 vendor 281ms, entry 89·80ms가 관찰됐다. **어느 함수가 긴 작업을 유발했는지는 확인하지 못했다.** 추가 headed CPU profiling은 브라우저 Target crashed로 결과를 얻지 못했다. 로딩 로고의 별도 300프레임 관찰에서 Canvas 그리기 CPU 중앙값 0.1ms/P95 0.3ms였지만 메인 TBT와는 범위가 다르다.

## 남은 검증과 전달 상태

기존 19항목 로딩 검사는 메인·목록·노트 데이터/모듈의 중앙 정렬과 준비 전환을 확인했다. 이후 요청된 **전체 화면 PendingApp/OAuth 로더의 중앙 정렬, 목록 스크롤 후 로더와 좁은 목록 로더, pending 버튼·저장 전환의 실제 시각 상태**는 그 검사로 확인되지 않았다. 각 상태를 실제 앱 화면에서 재현해 위치·전환·오류 표현을 다시 확인해야 한다. cold 메인 TBT의 정확한 함수 원인도 열려 있다. 이 항목들이 남아 있으므로 상위 #9와 하위 #8·#10~#14를 “전체 완료”로 취급하지 않는다. 과거에 GitHub 이슈가 `CLOSED / COMPLETED`로 기록된 것은 검증 범위나 원격 전달 완료의 근거가 아니다. 이슈 #5·#8~#14는 남은 검증과 전달 상태를 추적하도록 다시 열었다.

기존 검사에는 별도 QA 계정의 실제 저장·재조회·삭제 경로와 합성 인증·API 지연·실패 경로가 섞여 있다. 합성 경로는 실제 Google OAuth, 서버 장애, AI worker/LLM 호출의 검증이 아니다. 사용자 계정과 노트는 변경하지 않았다. 이 문서는 마지막 검증 시점의 결과를 보존하며, 이후 코드 변경에는 해당 경로의 재검증이 필요하다.

## 커밋 준비 확인 (2026-09-26)

Gemini 백엔드 병합을 가져온 기반 `77620ba`에서 웹 전체 타입 검사·ESLint·production build를 다시 실행했다. 타입 검사와 빌드는 통과했고 ESLint는 오류 0개·경고 12개였다. 기존 경고는 공용 UI의 React 19 `forwardRef` 권장 변경 7개와 반응형 크기 Hook의 Effect 상태 갱신 2개다. 이번 Graph 코드의 경고 3개는 빈 데이터에서 힘 설정을 초기화하고, 생성한 Three.js 장면을 렌더에 반영하고, D3 힘 설정 후 데이터를 전달하기 위한 Effect 상태 갱신이다. 코드 검토에서 조건과 의존성으로 반복 갱신을 제한함을 확인했으며 무한 렌더링 결함은 확인되지 않았다. 추가 렌더링 비용이 있으므로 경고를 숨기지 않고 남겼다. cold 메인의 장시간 작업 원인이라는 측정 증거는 없다. Graph/Milkdown의 큰 청크 경고도 남는다.

문서에서는 중복·중간 자료 59개(12,572,888바이트)를 삭제하고 대표 증거 28개를 남겼다. 공개할 이미지·JSON과 영상 표본에서 QA 내용만 확인했다. 갤러리의 이미지 18개 로드와 두 영상의 끝까지 재생을 기존 외부 Chrome 세션에서 확인했고 페이지 오류는 없었다. 이번 문서 정리 중 앱의 전체 회귀 검사를 다시 실행한 것은 아니다. 자동 검사 산출물은 `.playwright-cli/`에 저장하도록 바꿔 대표 자료를 덮어쓰지 않게 했다.

잘못 닫혔던 #5와 #8~#14는 다시 열고 로컬 커밋과 원격 전달을 구분했다. 이슈 종료에는 남은 필수 검증과 대상 브랜치의 PR 병합 확인이 필요하다. 이번 전달 범위는 로컬 커밋이며 푸시·PR·병합은 포함하지 않는다.
