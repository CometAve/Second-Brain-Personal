# 작업 계획·이슈·브랜치 기록 기준

이 문서는 [AGENTS.md](../../AGENTS.md)의 작업 기록 원칙을 구체화한다. 현재 요청과 승인된 범위를 먼저 확인한다. 이슈를 작성하거나 브랜치를 만든 사실만으로 구현·커밋·푸시·병합 권한이 생기지는 않는다.

## 작업을 시작할 때

1. 현재 요청, 브랜치, 작업 트리, 관련 열린 이슈, 이미 완료된 이슈의 기록을 확인한다. 관련된 열린 이슈가 같은 결과를 다루면 새로 만들지 않고 계획과 상태를 갱신한다. 정상적으로 완료된 이슈의 기록을 현재 작업으로 덮어쓰지 않는다. 새 범위의 후속 작업이면 새 이슈에서 이전 기록을 연결한다. 다만 미병합 변경이나 필수 검증 누락을 완료로 잘못 처리했다면 같은 이슈를 다시 열고 정정 이유와 남은 작업을 기록한다.
2. 구현 전에 **현재 문제와 확인한 근거**, **사용자에게 제공할 결과**, **범위와 진행 순서**, **먼저 끝나야 할 작업**, **검증 방법과 완료 기준**을 정한다. 아직 확인하지 못한 동작은 사실처럼 쓰지 않고 확인 과제로 표시한다.
3. 큰 목표는 상위 이슈에서 결과와 진행 상태를 추적한다. 독립적으로 구현·검증·완료할 수 있고 목적이나 선행 관계가 다른 일은 하위 이슈로 연결한다. 같은 화면·흐름에서 함께 검증할 작은 수정은 한 이슈의 체크리스트로 둔다. 파일 수, 버튼 수, 작업자 수만으로 이슈를 나누지 않는다.
4. 조사로 범위나 중요한 선택이 달라지면 이슈를 갱신한다. 작업 결과에는 실제 변경, 실행한 검사와 결과, 필요한 증거, 남은 문제와 미검증 범위를 적는다. 체크리스트의 완료 표시는 결과를 확인한 뒤에만 한다.

GitHub는 이슈 생성, 하위 이슈, 의존 관계, 이슈에서 브랜치 만들기 기능을 제공한다. 이는 사용할 수 있는 도구이며 모든 작업에 하위 이슈나 새 브랜치를 요구하지 않는다. [GitHub 이슈 생성](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/creating-an-issue), [하위 이슈](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/adding-sub-issues), [이슈 의존 관계](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/creating-issue-dependencies), [이슈에서 브랜치 만들기](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/creating-a-branch-for-an-issue)를 참고한다. 상위 이슈와 하위 이슈의 선택, 이슈 분할 기준은 이 프로젝트의 작업 방식이다.

## 이슈 본문 기본형

작은 작업에서는 항목을 합치거나 줄인다. 빈 항목을 채우기 위해 확인하지 않은 사실을 만들어 내지 않는다.

```md
## 왜 필요한가
어느 화면에서 어떤 불편이나 오류가 있는가? 확인한 사실과 미확인 내용을 나눈다.
버그라면 재현 순서, 현재 동작, 기대 동작을 적는다.

## 무엇을 바꾸나
작업 후 사용자가 보고 할 수 있게 되는 행동을 적는다.
이번 범위와 필요한 경우 제외 범위를 적는다.

## 작업 계획
- [ ] 구현·조사 단계
- [ ] 검증 단계

## 완료 기준
사용자 행동, 화면 결과, 데이터 보존, 필요한 검사로 확인할 조건을 적는다.

## 확인 방법
대상 화면·조작 순서·예상 결과·필요한 테스트 환경을 적는다.

## 연결된 작업과 결정
상위·하위·선행 이슈, 관련 PR, 중요한 선택과 이유를 필요한 만큼 적는다.

## 작업 결과
실제 변경, 실행한 검사와 결과, 화면 자료, 남은 문제와 미검증 범위를 갱신한다.
현재 상태: 계획 / 구현 중 / 로컬 구현·검증 완료(미커밋) / 로컬 커밋됨 / 푸시됨 / PR 검토 중 / 병합 확인.
```

제목과 설명은 처음 읽는 사람이 화면과 문제를 떠올릴 수 있도록 짧고 구체적으로 쓴다. 파일명이나 ‘품질 개선’ 같은 추상 표현보다 사용자 행동을 먼저 쓴다. 한 문장에는 한 가지 중심 내용을 담고, 원인·변경·결과를 자연스럽게 잇는다. 기술 용어가 필요하면 정확한 이름을 유지하고 뜻을 덧붙인다. 확인한 사실, 예정한 일, 모르는 점을 구분한다.

예를 들어 제목은 “노트 작성 화면에서 제목과 본문에 집중할 수 있도록 도구 배치 정리”, “창을 줄여도 노트 목록 버튼과 메뉴가 잘리지 않도록 수정”, “저장에 실패해도 입력한 내용을 유지하고 다시 저장할 수 있도록 수정”, “로고가 입체적인 구 형태로 회전하도록 로딩 화면 변경”처럼 결과를 드러낸다.

```md
# 창을 줄여도 노트 목록 버튼과 메뉴가 잘리지 않도록 수정

## 왜 필요한가
확인한 사실: 좁은 창에서 노트 목록을 여는 버튼의 일부가 가려진다.
확인할 내용: 메뉴를 연 뒤 키보드 포커스가 어디로 이동하는지.

## 무엇을 바꾸나
창 너비가 줄어도 목록 버튼과 열린 메뉴를 보고 조작할 수 있게 한다.

## 작업 계획
- [ ] 버튼과 메뉴의 배치 및 스크롤 영역 조정
- [ ] 좁은 창에서 마우스·키보드 조작 확인

## 완료 기준과 확인 방법
지정한 좁은 창 너비에서 목록을 열고 메뉴 항목을 클릭·키보드로 선택할 수 있다.
메뉴를 닫으면 포커스가 적절한 조작부로 돌아온다.

## 작업 결과
검증 전. 실제 수정과 검사 결과를 확인한 뒤 갱신한다.
```

예시의 ‘확인한 사실’은 작성 형식을 보여주는 가상 문장이다. 실제 이슈에는 재현한 환경과 근거가 있을 때만 그렇게 적는다.

## 상태와 전달 기록

- 계획과 완료 기준을 먼저 남기되, 조사 결과가 바뀌면 근거와 함께 조정한다. 관련된 이슈나 PR은 번호 또는 링크로 연결하고, 필요한 선행 작업을 명시한다.
- **로컬 구현·검증 완료(미커밋)**는 작업 트리에 코드가 있고 정해진 검증을 마쳤다는 뜻이다. 원격 저장소에 코드가 있다는 뜻이 아니다. **커밋됨**, **PR 검토 중**, **병합 확인**은 각각 별도 사실로 기록한다. 검사하지 못한 항목은 ‘미검증’이라고 적는다.
- **코드·설정·문서·개발 지침 등 저장소 변경이 있는 이슈는 필수 검증과 해당 PR의 대상 브랜치 병합을 확인하기 전까지 OPEN으로 유지한다.** 커밋을 만들었거나 원격에 푸시했어도 병합 전에는 닫지 않는다. 사용자가 미커밋 전달이나 커밋까지만 요청했다면 그 단계에서 작업을 전달하고 이슈는 열어 둔다. 이슈를 닫기 위해 푸시·PR·병합 권한을 임의로 확대하지 않는다.
- 이슈를 닫거나 PR에 자동 종료 키워드를 쓰기 전에는 그 이슈의 완료 기준, 필수 검증, PR의 포함 범위, 대상 브랜치를 확인한다. 완료 기준을 모두 충족하는 PR에만 `Closes #번호`를 쓰고, 병합 전에는 이슈를 수동으로 닫지 않는다. 일부만 전달하는 PR이나 미검증 항목이 남은 PR은 일반 이슈 링크로 연결한다. GitHub의 자동 종료는 기본 브랜치 병합에 연결되므로 다른 대상 브랜치인 경우 실제 병합을 확인한 뒤 상태를 갱신한다. [PR과 이슈 연결](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/linking-a-pull-request-to-an-issue)을 참고한다.
- 상위 이슈는 필요한 하위 작업의 전달과 통합 검증까지 끝나야 닫는다. 일부 하위 작업 완료나 체크리스트의 구현 항목 완료만으로 상위 이슈를 닫지 않는다.
- 저장소 변경이 없는 조사·질의 이슈는 합의된 결과와 검증을 전달한 뒤 닫을 수 있다. 취소·중복은 완료와 구분해 이유와 적절한 종료 상태를 남긴다. 사용자가 명시적으로 병합 전 종료를 지시한 경우에는 그 지시와 미병합 범위를 기록한다. 단순히 ‘커밋하라’는 요청은 조기 종료 지시가 아니다.
- 과거 완료 이슈는 증거와 결정을 찾는 기록이다. 새 범위의 발견을 과거 작업이 미완료였다는 뜻으로 바꾸지 않는다.

| 확인된 전달 단계 | 저장소 변경 이슈 상태 | 남길 증거 |
| --- | --- | --- |
| 구현 중 / 로컬 검증 완료(미커밋) | OPEN | 실제 검사 결과, 미검증 범위, 작업 브랜치 |
| 로컬 커밋됨 | OPEN | 커밋 SHA, 검증 결과, 미푸시 여부 |
| 푸시됨 / PR 검토 중 | OPEN | 원격 SHA, PR 링크와 대상 브랜치, 남은 검토·검증 |
| 필수 검증 충족 + PR 병합 확인 | CLOSED 가능 | 실제 병합 SHA, 대상 브랜치, 이슈 최종 상태 |

커밋 전에는 유지할 설명·재현 스크립트·대표 증거와 일회성 산출물을 구분한다. 중간 스크린샷·중복 영상·대형 원시 보고서는 필요한 결과를 요약한 뒤 커밋 대상에서 정리한다. 로컬에서 보존할 필요가 있으면 Git이 무시하는 위치로 옮기고, 남긴 문서의 링크와 개인정보·인증 정보 포함 여부를 확인한다. 제품 자산이나 사용자 데이터는 이 정리의 대상이 아니다.

## 브랜치 이름과 작업 단위

이슈의 본문과 실제 남은 일을 확인한 뒤 이름을 정한다. 프로젝트 이름 형식은 `codex/` 뒤에 목적이 드러나는 짧은 영문 소문자·하이픈 표현이다. 이슈 번호는 필요할 때 보조 정보로 넣되 번호만으로 이름을 짓지 않는다. 예: `codex/note-editor-layout`, `codex/graph-node-design`, `codex/3d-logo-loading`.

Git은 참조 이름에 공백·제어 문자와 `~`, `^`, `:`, `?`, `*`, `[` 등을 허용하지 않고 `..`, `@{`, 끝의 `.`, `.lock` 끝맺음 등도 제한한다. `git check-ref-format --branch <이름>`은 후보가 Git 브랜치명으로 유효한지 확인한다. 이 문서의 `codex/` 접두사와 소문자·하이픈·목적 중심 이름은 Git 자체의 요구가 아닌 프로젝트 규칙이다. [Git 참조 이름 규칙](https://git-scm.com/docs/git-check-ref-format), [Git 브랜치 문서](https://git-scm.com/docs/git-branch)를 참고한다.

새 브랜치가 실제로 필요할 때는 로컬·원격의 기존 이름과 다른 worktree 사용 여부를 먼저 확인하고 형식을 검사한다. 이슈 하나에 브랜치 하나를 기계적으로 대응시키지 않는다. 함께 검토하고 검증해야 할 변경과 이미 있는 미커밋 작업의 소유권을 고려한다. 현재 작업을 정리한다는 이유로 기존 브랜치를 임의로 바꾸거나 미커밋 내용을 지우지 않는다. 브랜치 생성·커밋·푸시·PR·병합은 각각 현재 요청의 권한과 [AGENTS.md의 Git 전달 경계](../../AGENTS.md#git-delivery-boundaries)를 따른다.
